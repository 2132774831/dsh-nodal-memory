# dsh-local-memory v2 设计定稿

> 状态：**v2 全部功能已实现并跑通** —— 内核 / 宿主层 / HTTP 接口 / 关系图 / 前端（含补标）/ 惰性维护 / 可选 embedding

## 一、分层：内核不活在宿主里

```
plugins/dsh-local-memory   ←  薄插件：注册工具、注入上下文、转发请求
        │  进程内 import（今天） / 本地 HTTP（将来）
        ▼
      core/                ←  记忆内核，零宿主依赖
```

**硬规则：`src/core/` 下的任何文件都不允许 import DSH / cordis / 插件 API。**
判断标准：需要访问宿主能力（注册工具、注入提示词、读会话）的需求 → 属于 `host/`，不属于 `core/`。

为什么这么分：这个系统要跑后台维护、要调外部模型、将来还要画节点图。这些都不适合塞进插件进程
——宿主一退出插件就死。内核独立之后，今天插件直接 `import`（零进程、零延迟），
将来做独立软件时同一份内核挂到本地 HTTP 上，插件只改调用方式，**不重写**。

## 二、存储：node:sqlite 为主，JSON 兜底

实测（2026-11-08，直接问宿主 exe）：

| 项 | 结果 |
|---|---|
| 宿主运行时 | Electron 44.7.0 / Node 24.21.0 |
| `node:sqlite` | 内置可用；WAL ✓ FTS5 ✓ `bm25()` ✓ integrity_check ✓ |

所以主力走 SQLite：零依赖白拿事务、索引、全文检索。不需要 `better-sqlite3` 这类原生模块
（原生模块在插件分发里会因 ABI / 平台不匹配炸掉，那是最贵的一类 bug）。

`engines.node >= 20` 意味着在 Node 20 上没有 `node:sqlite`，此时自动退回单 JSON 文件
（纯 JS 打分）。**装得上、不崩**优先于"永远最快"。

### 为什么不需要文件锁

设计文档建议"写前检查 lock 文件"——那是错的，典型 TOCTOU：检查和写入之间别人插进来，锁毫无作用。

这里不需要锁，因为：
1. 所有读写都在**同一个宿主进程**内；
2. 每个操作都是**同步**的（`DatabaseSync` 是同步 API，JSON 后端是同步改内存 + 原子落盘）；
3. Node 单线程，同步操作之间不可能交错。

真需要跨进程时，正确做法是 SQLite 的 `BEGIN IMMEDIATE`，不是"文件是否存在"。

## 三、中文检索：自己切 bigram

这是整个内核里最容易做错、且做错了**不报错只搜不到**的地方。实测结论：

| 分词器 | 「牛肉面」 | 「北京」 | 结论 |
|---|---|---|---|
| `unicode61`（FTS5 默认） | 0 命中 | 0 命中 | 中文整句被当成一个 token，废 |
| `trigram` | 1 命中 | **0 命中** | 至少需 3 字符，中文两字词全废 |
| **bigram（自建）** | ✓ | ✓ | 两字/三字/英文全通，且「北京市」不乱命中 |

做法：入库时把正文切成二元组存进 FTS 专用列（`我喜欢吃牛肉面` → `我喜 喜欢 欢吃 吃牛 牛肉 肉面`），
查询时把 query 也切成 bigram。**英文和数字保持整词**，否则查 `me` 会命中 `memory`。

### 召回与精度的两难，以及解法

一句中文会切成多个 bigram（`记忆插件` → `记忆/忆插/插件`）：
- 用 AND：只要原文不是逐字连续出现就 0 命中（实测漏掉一半相关记忆）
- 用 OR：一堆"只沾一个字"的噪声

解法是 **OR 取候选 + 覆盖率阈值把关**：命中 token 比例低于阈值（短查询 50%、长句放宽到 30–40%）直接丢弃。
实测「记忆插件」从 1 条恢复到 5 条，且逐字连续的排第一（`matchedTokens 3/3`）。

## 四、打分公式

```
score = relevance × importanceFactor × decay × usageBoost
```

| 因子 | 取值 | 说明 |
|---|---|---|
| `relevance` | 0~1 | SQLite：`0.5×bm25归一 + 0.5×token覆盖率`；JSON：覆盖率。两后端语义对齐 |
| `importanceFactor` | 0.6~1.0 | key 1.0 / important 0.8 / casual 0.5 / transient 0.25。**下限 0.6 不是 0**——重要性只调节排序，不该让一条记忆彻底消失 |
| `decay` | 0~1 | 半衰期：work 365 天、preference 730 天、emotion 60 天、unknown 365 天。用半衰期而不是 `exp(-λt)`，好解释好调 |
| `usageBoost` | 1~ | `1 + 0.15·ln(1+accessCount)`，对数压制防止高频记忆永久霸榜 |

**为什么不用"向量相似度×(…)"那套**：本机没有 embedding 端点时那套直接成 NaN。
这个公式在零外部依赖下就能工作；将来接上 embedding，只把 `relevance` 换成混合分，其余不动。

## 五、数据 schema（SQLite）

`memory` 表主键是两个：`rid`（自增整数，给 FTS5 的 rowid 用）+ `id`（TEXT，沿用 v1 的 `m-xxx`，历史引用不断链）。

关键字段与理由：

| 字段 | 为什么这么设计 |
|---|---|
| `deleted_at` | **软删**。删对话删出过事，记忆更不能物理删。真删只走 `purge()` 且必须显式调用 |
| `kind` | work / emotion / preference / unknown 四值。加 `unknown` 是因为 v1 老数据没法判断，**不猜** |
| `importance` | 枚举而非 1-5 主观分。让模型打 1-5 分不稳定，同名分数不同含义；枚举可校验 |
| `injected_count` / `searched_count` | 分两个计数：系统自动注入 vs 模型主动检索。两者比值能看出哪些记忆是"真有用" |
| `origin` | 标记 `v1` / `v2`，迁移来的老数据可回溯 |
| `schema_version` | 结构演进时做迁移判断，不会读不懂就崩 |

`memory_update` 表（updates 时间轴）和 `memory_meta`（键值元信息）结构已就位，本阶段未启用。

## 六、迁移（v1 → v2）

- **只读源文件**，跑完校验源库 SHA256 未变
- **幂等**：已存在的 id 跳过，不覆盖。重跑不会把 v2 累积的使用计数冲回 v1 旧值
- 字段映射：`text→content`、`hits→accessCount+searchedCount`、`lastUsedAt→lastAccessed`、`project` 下划线统一成连字符
- 两处保守判断：`kind` 只有带 `pref` 标签的判为 preference，其余 `unknown`（**不猜 work/emotion，猜错比不猜更有害**）；`importance` 统一 `important`

实测：真实库 70 条全部落库，0 无效，源库哈希未变。

## 七、已知限制（诚实列出，不藏）

1. **单字中文查询**（如「鱼」）能命中含该字的记忆，但只匹配"单字成词"的情况，精度不高，需要时再补 LIKE 降级。
2. **跨词查询**（「北京市」查「北京」）不会命中——bigram AND 语义要求相邻。属于精度优先的取舍。
3. **JSON 兜底后端是 O(n) 全表扫**，几万条会慢。这是主力走 SQLite 的原因。
4. `kind`/`importance` 对 63 条迁移数据是 `unknown`/`important`，需要后续"补标"流程，本阶段没做。
5. embedding 层、节点图、维护任务（惰性触发）、回收站 UI —— **都还没做**。

## 九、HTTP 接口

前缀 `/dsh-local-memory`，`ctx.webServer.register({kind:'prefix'})` 挂载。

**每个请求都必须过信任栅栏**（`ctx.get('connection').requestRejection(req)`）——
不过这一关，用户随手打开的任何网页都能 fetch 到本机接口读写记忆库。

| 方法 | 路径 | 作用 |
|---|---|---|
| GET | `/state` | 配置 + 统计 + 后端类型 |
| GET | `/memories` | 列表；带 `q` 走检索、带 `includeDeleted=1` 看已删 |
| POST | `/memories` | 新增 |
| POST | `/memories/:id` | 更新 |
| DELETE | `/memories/:id` | **软删** |
| POST | `/memories/:id/restore` | 恢复 |
| POST | `/memories/:id/purge` | 彻底删除（必须显式调用） |
| GET | `/graph` | 关系图的点与边（服务端算好，前端只画） |
| GET | `/review` | 体检报告 |
| POST | `/config` | 局部更新配置 |
| GET | `/export` | 导出 Markdown |

## 十、关系图算法

**核心判断：边不能靠"语义相似度"。** 纯本地算不出可靠语义，硬算就是噪声。只用四种确定性关系：

| 关系 | 权重 | 说明 |
|---|---|---|
| 共现 | `1 + ln(1+count)` 最强 | 同一次检索/注入里同时出现 —— 使用痕迹，云端拿不到 |
| 共享标签 | `ln(1 + n/freq)` | idf：越冷门的标签绑得越紧 |
| 同项目 | 0.4 | 弱，主要用于把同一次工作的产出聚成团 |
| 时间相邻 | ≤0.15 | 最弱，只连时间上最近的一条，纯布局用 |

### 三条防"毛线球"的防线（都是被真实数据逼出来的）

1. **泛滥标签不画**：出现在超过 30% 记忆上的标签直接跳过（真实数据里 `pitfall`、`topic:dsh-plugin` 就属于这类）
2. **超大分组不画**：一个分组超过 12 个成员就整组不连。真实数据里 `default-workspace` 有 59 条记忆，两两相连 = 1711 条边，画出来是一团黑，等于什么都没说
3. **边数上限 + 按权重截断**

实测效果（真实 73 条）：**2126 条边 → 277 条边**，并且从"一个孤岛都看不见"变成 **10 个孤岛**。

### 孤岛判定只看"有语义"的边

节点有两个度数：`degree`（含时间边，给布局用）和 `linkDegree`（只算标签/项目/共现）。
`isolated` 看的是后者。

原因：时间相邻会把所有创建时间接近的记忆串成一条链，如果按总度数判孤岛，就永远不会出现孤岛——
而用户要看的恰恰是"写了但没人用"的那些记忆。

## 十一、前端

单文件 `src/client/index.js`（740 行），**没有构建步骤**——`window.__ModuleLoader__.load({id, factory})`，
`id` 必须等于 loader entry 名。两个页签注册在 `settings.section`（id `local-memory`，order 28）。

为什么前端不自己算关系：边是**服务端**算好的（四类确定性关系 + 三道防毛线球防线）。
前端只负责布局与绘制。这样将来做独立软件时，换个渲染器就能复用同一份图数据。

### 力导向布局的几个坑

- **初始位置沿圆周铺开**：全从原点出发时，第一步斥力会算出 0 距离，除以接近 0 的数
  会瞬间把坐标炸成 NaN，整张图直接消失。这是这类动画最经典的死法。
- **速度上限 + 数值兜底**：一次异常大的力就能把点甩到几万像素外；即使真出 NaN 也重摆回圆周。
- **收敛后停 rAF**：`alpha` 衰减到 0.02 以下就停，否则一直空转烧 CPU。
- **收敛提示只 setState 一次**：每帧都 `setStats` 会每帧触发重渲染，等于自造渲染死循环。
- **标签只标连接多的点，并且带深色描边底衬**：全标会糊成一团；亮色字压在密集连线上读不清。

布局数学通过 `exports.__internals` 暴露给 `test/client.test.mjs`（14 项），
专门测 NaN、收敛、以及"有边相连的两点最终确实更近"——这些只能在数学层面抓。

### 不装插件也能先看图

`node scripts/graph-preview.mjs` 会用**同一套布局算法和同一组配色常量**把真实数据渲染成 SVG。
渲染器不同（SVG vs canvas），所以它只是给眼睛看的快照，交互只有真界面才有。

### 补标（第三个页签）

v1 迁移过来的数据没有 `kind`，实测真实库 74 条里有 **67 条未分类**——图上全是灰点。
补标页签专门解决这个：逐条读正文，点「工作/偏好/情感」，顺手还能改重要度和标签。

**为什么不做批量全选**：分类必须逐条读正文才能判断，批量操作只会制造一堆看起来整齐
其实错分的标签，比不分类更糟。所以一次只推进一条——分完类自动从队列里消失。

分类只影响检索排序和图的着色，**不丢记忆**，写错随时改。

## 十二、惰性维护

**不用 `setInterval`**。宿主的生命周期不可预测：可能几小时就退、可能休眠一夜、也可能连开三天。
定时器在这三种情况下分别是「跑了没用」「根本没跑」「漂移得离谱」，而且会在进程里留一个
永不结束的句柄，卸载忘了清就是泄漏。

改成**惰性触发**：每次"用到库"的时候看一眼 `last_maintenance_at`，超过
`maintenanceIntervalDays`（默认 7 天）才真正干活。检查本身只是一次 meta 读取，可忽略。

### 维护只做绝对安全的事

| 做 | 不做 |
|---|---|
| 清孤儿共现行（指向已不存在的记忆） | ❌ 自动删记忆 |
| 清孤儿 updates 行 | ❌ 自动改 status |
| 记一份统计快照（总数/从未用过/完整性） | ❌ 自动合并"重复"记忆 |
| SQLite `PRAGMA integrity_check` | ❌ 自动降权 |

理由：自动遗忘一旦误判就是**不可逆的数据损失**，不值得为省那点空间去冒。
哪怕一条记忆三年没人用过，删不删也由人决定。

维护失败不会抛到调用方（写入路径不能因为维护挂掉而炸），而且**失败也会记时间戳**——
否则每次写入都会重试同一次失败，等于把库锁死在一个坏状态上。

手动触发：`POST /dsh-local-memory/maintenance`（只接受 POST，避免浏览器地址栏误触发）。
`GET /state` 会带上 `maintenance.lastAgoDays`，界面可以显示"上次维护多久前"。
